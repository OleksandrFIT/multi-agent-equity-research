# A3 — Meaningful backtest (measuring instrument) — design

Дата: 2026-09-16
Статус: чернетка на затвердження
Частина: A3 (напрями 2+3). «Вимірювальний прилад», щоб бачити, чи Q1/Q3 (і майбутні зміни) реально
покращують передбачення, а не лише читабельність.

## Мета
1. **Per-record деталізація** звіту: по кожному (тікер × дата) — вердикт, score, forward-дохідність
   21/63д, «вгадав/ні». Закриває скаргу «незрозуміло, які дані по якій акції».
2. **Чистіший, більший набір** для статистично осмисленого IC (замість шуму n=20).
3. **Прогін і вимір**: запустити й порівняти IC (до/після Q1+Q3).

## Проблеми поточного backtest
- Universe містить KO/XOM (краш `company_facts` → fundamentals пропускається) і JPM (банк →
  спотворений revenue_growth). n=20 — статистичний шум.
- Звіт лише агрегатний — не видно, який вердикт по якій акції/даті та чи справдився.

## Дизайн

### Backend — per-record у звіті
- `render_backtest_json`: додати масив `records`: `[{ticker, as_of, verdict, score,
  fwd_returns: {"21": x, "63": y}}]` (із наявних `BacktestRecord`).
- `render_backtest_markdown`: додати таблицю per-record під агрегатами.
- Ендпоінт `/api/backtest` уже шле report через `render_backtest_json` → `records` доїде на фронт.

### Backend — чистіший/більший набір (config.yaml `backtest`)
- Universe: ~10 **нефінансових** мегакапів, що не спотворюють фундаментал (financials виключаємо;
  тікери, де `company_facts` падає, лишаємо — fundamentals просто пропуститься, це не краш):
  AAPL, MSFT, NVDA, META, GOOGL, AMZN, JNJ, PEP, CSCO, HD.
- Dates: 6 квартальних точок 2023–2024 (напр. 2023-06-15, 2023-09-15, 2023-12-15, 2024-03-15,
  2024-06-14, 2024-09-13). Разом ~60 записів × 2 горизонти. **Масштаб — на підтвердження нижче.**
- Horizons: лишаємо [21, 63].

### Frontend — таблиця per-record
- У `BacktestReportView`: під StatTiles додати компактну таблицю
  (тікер · дата · вердикт-бейдж · score · fwd 21д · fwd 63д, кольори по знаку) — скрол у контейнері.
- Тип `BacktestReport` розширюємо полем `records`.

### Прогін і вимір (CONTROLLER-LIVE)
- Запустити розширений backtest у фоні (це **години** на 7B+PM), зібрати report, доповісти:
  IC 21/63, hit/mean по класах, і **порівняння** з попереднім IC≈−0.16.
- Це разова діагностика, не блокує решту.

## Файли
- `equity_research/eval/report.py` — `records` у JSON + md-таблиця.
- `config.yaml` — новий universe/dates.
- Frontend: `src/api/types.ts` (`records`), `src/components/BacktestReport.tsx` (таблиця).
- Тести: `tests/test_report.py` (records у JSON + md-таблиця); Vitest на таблицю.

## Тестування
- Backend (детерміновано): `render_backtest_json` містить `records` із коректними полями на
  фейкових `BacktestRecord`; markdown має рядок таблиці.
- Frontend: `BacktestReportView` рендерить рядки records із фікстури.
- Жива: розширений backtest дає report із records; фронт показує таблицю; IC зафіксовано й порівняно.

## Чесні застереження
- Навіть n≈60 — помірна вибірка; IC лишається орієнтиром, не доказом edge. Але це на порядок краще
  за n=20 і дозволяє бачити напрям змін.
- Прогін довгий; його робимо як фонову діагностику.

## Відкриті рішення (підтвердити)
1. **Масштаб/час:** (a) помірний 10×6=60 (~2–3 год), (b) більший 12×8=96 (~4–5 год),
   (c) швидкий 6×4=24 чистими тікерами (~40 хв, менш значущий). Пропоную (a).
2. **Таблиця per-record на фронті зараз** (реком., закриває твою скаргу) чи лише backend-звіт?

## Поза межами
Калібрація вердиктів історією (окремо); зміна метрик IC; A1/A2/Q2.
